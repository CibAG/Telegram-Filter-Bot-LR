# Python Development

Применяй этот навык при написании, изменении, рефакторинге и отладке Python-кода в проекте `D:\Python\Bot`.

## Границы работы

- Изменяй файлы только внутри `D:\Python\Bot`.
- Не трогай глобальный Python, системные пакеты и другие проекты пользователя.
- Для зависимостей используй виртуальное окружение `.venv` внутри проекта.

## Секреты и API-ключи

В проекте могут использоваться API-ключи и токены. Они не должны попадать в код, логи, git и сообщения.

- Никогда не записывай реальные ключи в `.py`, конфиги, тесты, README или примеры.
- Единственное место хранения: `.env` (или переменные окружения ОС). Файл `.env` уже в `.gitignore`.
- Для локального запуска загружай `.env` через `python-dotenv` (`load_dotenv()`); в проде используй переменные окружения.
- В коде читай секреты только из окружения, например через `os.environ["API_KEY"]` или `os.getenv("API_KEY")`; при отсутствии — понятная ошибка без вывода значения.
- Для примеров используй `.env.example` с заглушками, например `API_KEY=your_api_key_here`.
- Не выводи ключи через `print`, `logging`, `repr`, трассировки и тексты исключений. При логировании маскируй: первые/последние 2–4 символа.
- Не вставляй реальные ключи в чат, коммиты, issue, скриншоты и отчёты. Если ключ нужен для проверки — попроси пользователя добавить его в `.env` самостоятельно.
- Перед коммитом проверяй diff и индекс на секреты: `git diff`, `git diff --cached`, `git status`.
- Если ключ всё же оказался в git или в переписке — считай его скомпрометированным: сообщи пользователю, что ключ нужно немедленно отозвать/перевыпустить. Удаления из файла недостаточно, история git сохраняет значение.

## OpenRouter

Проект использует OpenRouter как единый шлюз к AI-моделям.

- Ключ хранится только в `OPENROUTER_API_KEY` (`.env` / окружение ОС), никогда в коде.
- Базовый URL: `https://openrouter.ai/api/v1`; модель задавай через `OPENROUTER_MODEL`, не хардкодь её по всему коду.
- OpenRouter совместим с OpenAI SDK, поэтому можно использовать `openai` с `base_url`. Альтернатива — официальный пакет `openrouter`.
- Таймауты и повторные попытки (429, 5xx) настраивай явно; не делай бесконечных ретраев.
- Не логируй заголовок `Authorization`, тело запроса с приватными данными и полные ответы модели.
- Не отправляй в промпты API-ключи, токены, персональные данные и содержимое `.env`.
- Модель и стоимость — параметры конфигурации: проверяй актуальные слаги и цены на <https://openrouter.ai/models>.
- Ошибки API обрабатывай по коду статуса и возвращай понятное сообщение без внутренних деталей.

Минимальный клиент:

```python
import os

from openai import OpenAI

client = OpenAI(
    base_url=os.getenv("OPENROUTER_BASE_URL", "https://openrouter.ai/api/v1"),
    api_key=os.environ["OPENROUTER_API_KEY"],
)

response = client.chat.completions.create(
    model=os.environ["OPENROUTER_MODEL"],
    messages=[{"role": "user", "content": "Привет"}],
    timeout=60,
)
```

## Текущий проект

- `D:\Python\Bot` — Telegram-бот модерации версии 1.0.0.
- Стек: aiogram 3, SQLAlchemy 2 (async) + SQLite, pydantic-settings, OpenRouter.
- Запуск: `.\.venv\Scripts\python.exe -m app.main` или `start_bot.bat`.
- Проверки: `.\.venv\Scripts\ruff.exe check .` и `.\.venv\Scripts\python.exe -m pytest -q`.
- Точка входа: `app/main.py`; обработчики — `app/handlers` (личка, панель, модерация, диалоги), модели — `app/db/models.py`.
- **Всё управление ботом — только в личке администратора.** В группах нет команд,
  кнопок и служебных сообщений; там бот только молча удаляет нарушения.
- Чаты и темы регистрируются `TrackingMiddleware` по сообщениям в группах
  (Telegram не отдаёт полный список тем через API).
- Не читай и не выводи содержимое `.env`; для диагностики проверяй только наличие ключей.
- Подробности и ограничения — в `README.md`.

## Рабочий процесс

1. Изучи существующую структуру проекта и стиль кода, прежде чем добавлять файлы.
2. Проверь `pyproject.toml` / `requirements.txt`; новые зависимости добавляй только при реальной необходимости и сообщай о них.
3. Вноси минимальные, сфокусированные изменения, сохраняя стиль окружения.
4. После изменений запусти доступные проверки:
   - `python -m compileall -q .` — синтаксис;
   - `pytest` — тесты, если они есть;
   - `ruff check .` и `ruff format --check .` — линт и форматирование, если настроены.
5. Если проверки запустить нельзя, явно скажи почему.

## Соглашения

- Python 3.10+; используй аннотации типов в новом коде.
- Публичные функции и классы сопровождай кратким docstring.
- Предпочитай `pathlib.Path` вместо ручной склейки путей.
- Не оставляй отладочные `print`, закомментированный код и секреты в репозитории.
- Секреты читай из переменных окружения или `.env`; `.env` не коммить.
- Для ошибок используй конкретные исключения, не глуши `except Exception` без логирования.
